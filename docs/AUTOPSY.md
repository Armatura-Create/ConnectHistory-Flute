# Автопсия старого модуля ConnectionStats

Модуль-предшественник (`flute_plugins/ConnectionStats`, 2024) написан под старый плагин
и на Flute 1.0.7 не работает. Переносить из него нечего: он читает таблицу `history`
(`account_id`, `date`, `session_time`), которой в схеме нового плагина нет.

Ценность в нём одна — **список того, как этот класс задач ломается на этом стеке**.
Восемь отказов, оплаченных боевой эксплуатацией. Каждый разобран до корневой причины
и закрыт архитектурой нового модуля, а не заплаткой.

Проверяемые без Flute пункты вынесены в `tests/` и стоят в CI с первого дня.

---

## №1. Админка ложится на длинном периоде

**Симптом.** Выбор «180 дн.» или «360 дн.» в селекторе — белая страница,
`Allowed memory size exhausted` в логе PHP.

**Где.** `Services/ConnectionStats.php:118-160`, `fetchData()`.

**Корневая причина.** Запрос без `LIMIT` и без агрегации:

```php
$query = dbal()->database($server['db'])->select()
    ->from('history')
    ->where('server_id', $server['additional']->sid)
    ->andWhere('date', '>=', $periodTimestamp)
    ->orderBy('date', 'ASC');
// ...
return $query->fetchAll();   // ← вся история за период в PHP-массив
```

Дальше `prepareChartData()` считает группировку по датам циклом `foreach` в PHP.
Стоимость страницы линейна по числу сессий: 500k строк за год — это сотни мегабайт
массивов ради графика из 365 точек.

**Что делает это невозможным в новом модуле.**
`HistoryRepository` не возвращает сырые строки для аналитики — только результат
`GROUP BY`. Таблицы отдают `SelectQuery` прямо в `LayoutFactory::table()`, пагинацию
и `LIMIT` ставит платформа. Период клампится в `SessionFilter` на входе.
Правило: **агрегат считается в SQL**. Строка сессии попадает в PHP только если
её видно на экране.

**Тест.** `tests/SessionFilterTest.php` — период всегда в допустимом окне,
произвольные даты не расширяют его за верхнюю границу.

## №2. Fatal error на приватном Steam-профиле

**Симптом.** `Attempt to read property "avatar" on null` — раздел не открывается,
пока конкретный игрок остаётся в последней десятке.

**Где.** `Services/ConnectionStats.php:96`, `getLastTenPlayers()`.

**Корневая причина.**

```php
$avatars = steam()->getUsers($steamId64s);

foreach ($data as $key => $val) {
    $data[$key]['avatar'] = $avatars[$val['account_id']]->avatar;  // ← без проверки
}
```

Отсутствующий профиль трактуется как аномалия. На деле это норма: профиль может быть
приватным, удалённым, а Steam Web API — просто недоступным. Плюс блокирующий внешний
вызов на каждый рендер страницы, без кеша.

**Что делает это невозможным в новом модуле.**
`PlayerIdentityService` строит личность игрока по трёхуровневой цепочке, где каждый
уровень — обычная ветка, а не исключение:
1. пользователь Flute по привязанному Steam (аватар и ник уже локально);
2. `steam()->getUsersInfo()` одной пачкой на страницу, результат в кеш;
3. `nickname` из `ch_sessions` + ссылка на steamcommunity по `steamid64`.

Третий уровень доступен всегда и не требует сети. Отсутствие профиля не может уронить
страницу, потому что «профиля нет» — это одно из штатных состояний.

**Тест.** `tests/PlayerIdentityTest.php` — пустой ответ Steam, частичный ответ,
исключение транспорта: во всех случаях личность построена.

## №3. Раздел доступен всем, кто дошёл до `/admin`

**Симптом.** Любой пользователь с минимальным доступом в панель видит историю
подключений целиком, включая колонки персональных данных.

**Где.** `Services/ConnectionStats.php:23-33`, `init()`.

**Корневая причина.** Проверки прав нет вообще. Единственное условие — совпадение пути:

```php
if (!(request()->is('/admin/') || request()->is('/admin')))
    return;
```

Глубже: персональные данные (IP, город) и игровая статистика лежат в одной таблице
и в модуле ничем не разделены. Разграничение просто негде было выразить.

**Что делает это невозможным в новом модуле.**
Два права вместо одного:
- `admin.connecthistory` — просмотр раздела (`Screen::$permission`);
- `admin.connecthistory.pii` — `player_ip`, `city`, `ip_subnet`, `ip_hash`.

Ключевое: без второго права эти колонки **не попадают в список `SELECT`** —
`HistoryRepository` формирует набор полей из прав, а не прячет их в вёрстке.
Утечка становится физически невозможной, а не «не предусмотренной интерфейсом».

**Тест.** `tests/ColumnAccessTest.php` — набор колонок без права `pii` не содержит
ни одного персонального поля.

## №4. Модуль не устанавливается

**Симптом.** `Class "Flute\Core\Modules\ModuleInformation" not found` при активации.

**Где.** `Installer.php:7`.

**Корневая причина.** Класс переехал: `Flute\Core\Modules\ModuleInformation` →
`Flute\Core\ModulesManager\ModuleInformation`. Модуль об этом узнал в проде.

**Что делает это невозможным в новом модуле.**
Job `flute-compat` в CI: ставит `flute-cms/cms` целевой версии и проверяет, что каждый
импортируемый модулем класс `Flute\*` существует. Переезд класса ловится на PR,
а не при активации на боевом сайте.

**Тест.** `tests/compat/assert-flute-classes.php` (запускается только в CI, где доступен Flute).

## №5. Fatal error на фильтре «новые игроки»

**Симптом.** `Class "Spiral\Database\Injection\Parameter" not found` — падает только
при включённом фильтре, поэтому не видно при беглой проверке.

**Где.** `Services/ConnectionStats.php:8` (импорт) и `:140` (использование).

**Корневая причина.** Та же, что в №4: `Spiral\Database\Injection\Parameter` стал
`Cycle\Database\Injection\Parameter`. Отдельный пункт, потому что ломается не при
установке, а на конкретной ветке кода — и показывает, что «модуль открылся»
не равно «модуль работает».

**Что делает это невозможным в новом модуле.** См. №4. Дополнительно: PHPStan level 5
в том же job проходит по всем веткам, а не только по тем, что кто-то открыл руками.

## №6. `Attempt to read property on array`

**Симптом.** Ошибка на серверах, где в настройках подключения не заполнено
дополнительное поле.

**Где.** `Services/ConnectionStats.php:232` (заполнение) и `:121`, `:107` (чтение).

**Корневая причина.** Тип поля зависит от данных:

```php
'additional' => $mode->additional ? \Nette\Utils\Json::decode($mode->additional) : [],
```

При заполненном поле — объект, при пустом — массив. Читают всегда как объект
(`$server['additional']->sid`). Плюс `Json::decode` бросает на битом JSON,
и это нигде не перехвачено.

**Что делает это невозможным в новом модуле.**
`ConnectHistoryModDriver` объявляет `getValidationRules()` — панель не даёт сохранить
подключение без `server_id`. Чтение идёт через один типизованный метод, который
возвращает значение по умолчанию на любом кривом входе, включая невалидный JSON.
Тип не зависит от наличия данных.

**Тест.** `tests/ModDriverTest.php` — `null`, `''`, `'{'`, `'[]'`, `'{"server_id":"3"}'`
дают предсказуемый результат без исключений.

## №7. График показывает не то, что подписано

**Симптом.** «История подключений» — всегда монотонно растущая кривая. Провалы
посещаемости на ней увидеть нельзя в принципе.

**Где.** `Services/ConnectionStats.php:186-196`, `prepareChartData()`.

**Корневая причина.**

```php
$cumulativeTotal = 0;
foreach ($accumulatedData as $date => $count) {
    $cumulativeTotal += $count;          // ← накопительная сумма
    $chartData['totals'][] = $cumulativeTotal;
}
```

Рисуется накопительный итог, подписанный как динамика. Тихая ошибка: график
выглядит правдоподобно и не вызывает подозрений, но отвечает на другой вопрос.

**Что делает это невозможным в новом модуле.**
Каждая вкладка «Обзора» — один агрегирующий запрос, чьё имя совпадает с подписью:
заходы по дням — `COUNT(*) ... GROUP BY DATE(started_at)`, динамика онлайна —
`AVG(players)`/`MAX(players)` из `ch_online_snapshots`. Никаких вычислений между
запросом и графиком, где смысл мог бы разойтись с подписью.

## №8. Лишний запрос в БД на каждый запрос к панели

**Симптом.** Незаметен по отдельности, виден в профайлере: `populateServerModes()`
выполняется на любом обращении к панели, даже когда раздел не открывают.

**Где.** `ServiceProviders/ConnectionStatsServiceProvider.php:13` → `ConnectionStats::init()`.

**Корневая причина.** Провайдер вызывает `init()` в `boot()`, то есть работа делается
на этапе загрузки модуля. Ранний `return` по проверке пути срабатывает **после**
входа в метод, но выборка серверов идёт до отрисовки — и до любой проверки прав (№3).
Экран рисуется push-ем в чужую секцию (`@push('admin-main::charts')`), поэтому
у модуля нет собственного маршрута, на котором можно было бы что-то проверить.

**Что делает это невозможным в новом модуле.**
`boot()` только регистрирует: `bootstrapModule()`, драйвер, admin-package, переводы.
Ни одного запроса к БД. Данные читаются в `Screen::mount()` — то есть когда открыт
конкретный маршрут, объявленный в `Admin/Package/routes.php`, и после проверки
`Screen::$permission`.

## Сводка правил, выведенных из отказов

| Правило | Закрывает |
|---|---|
| Агрегат считается в SQL, не в PHP | №1 |
| Отсутствие внешних данных — штатная ветка, не исключение | №2 |
| Права определяют список `SELECT`, а не видимость в вёрстке | №3 |
| Совместимость с CMS проверяется в CI, а не в проде | №4, №5 |
| Тип значения не зависит от того, заполнено ли оно | №6 |
| Подпись графика = имя агрегата, между ними нет вычислений | №7 |
| `boot()` регистрирует, `mount()` читает | №8 |
